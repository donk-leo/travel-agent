## 0. 现状与 5 个最痛体验问题

只列能被文件与行号核对的现状；每一条都在本规格里有对应改法。

| # | 现状（可核对证据） | 用户实际感受到的 | 本规格对应 |
|---|---|---|---|
| P1 | **结果页是调试面板**：`web_app.py` 的 `PAGE` 是纯 HTML 字符串，无 `<style>`/`<script>`/`<!doctype>`/viewport（T0.2 用 Python 检查四项，输出全部 `False`）；页面共 7 个并列 `<h2>`，结果区第二块就是“提取出的旅行约束”＋`<pre>{{ intent_json }}</pre>`（`web_app.py:33–36`），主视图还直出“路线结构：X 个地点、Y 段 NEXT 连接”（`web_app.py:127–133`），无匹配时最多列 10000 条地点且不分景点/餐饮/交通（`web_app.py:69–88`）。 | 像在看日志；手机上 JSON 横向溢出；不知道该看哪一块。 | §4.1、§4.2、§9 |
| P2 | **等待期间没有任何反馈**：提交是同步 POST，`run_agent` 返回前页面不刷新（`web_app.py:236–241`）；单次模型调用超时 180 秒（`intent_parser.py:95`、`tool_selector.py:85` 等 8 处 `timeout=180`）；历史单次查询 33–158 秒（BASELINE.md §6，**非本次复测**）。 | 白屏 1–3 分钟，不知道程序是否还活着，只能反复点提交。 | §3 J1、§8、§9 N1 |
| P3 | **状态不可见，且旧词会误导**：页面从不渲染 `result["status"]`（`web_app.py` 全文 grep `status` 为 0 命中）；后端仍产出 `working`/`complete`/`reply`/`partial`/`clarify`/`error`（`agent.py:98`、`207`、`220`、`181`）。 | `complete` 被读成“一天走得完”；`partial` 与 `error` 在页面上长得一样；用户无从判断该不该信。 | §5 |
| P4 | **证据只剩编号**：来源只出现在折叠区 `<details>查看每段路线的图谱来源`，内容是 `source_doc_ids|join("、")`（`web_app.py:144–154`、`180–190`），没有标题、URL、发布日期、原文摘句。 | 用户无法核对，只能选择相信或不信；答辩时也无法当场点开原文。 | §6 |
| P5 | **行程是模板，不是可执行的一天**：时段时长写死在 `PERIOD_HINTS`（`itinerary.py:11–15`：上午/下午 2–3 小时、中午 1–1.5 小时），页面直接显示“（建议预留 2–3 小时）”却不标依据（`web_app.py:62`）；多日按节点数均分（`itinerary.py:49`、`138`）；餐饮只有“请在园区内选择营业的餐厅”（`itinerary.py:52–55`）；人群/体力只在结尾一段提示，没有限制或置顶。 | 带老人孩子照这条走会崩；不知道哪段时长有出处、哪段是估的。 | §7 |

> 结论：现在缺的不是功能数量，而是**可信**（P3/P4）、**可执行**（P5）、**可读**（P1/P2）三件事。本规格只解决这三件事。

## 1. 一句话主张与非目标

### 1.1 页面顶部固定文案（可直接使用）

主标题（h1，全页唯一）：

> **可核验的景区行程助手**

副标题（主张，一行，移动端折行后不超过 3 行）：

> 每条路线都有出处，每个不确定都标出来；不编距离、不编时间、不编开放信息。

第三行（覆盖范围与时效，跟着主张走，小字）：

> 目前只覆盖 **长隆 / 白云山 / 武功山**，只用已采集的公开资料（当前 29 篇，见 BASELINE.md 第 3 节）。没有实时票价、排队、天气与开放状态。

### 1.2 三条永远不出现在页面上的表述（硬禁）

1. “一天玩遍/轻松走完/不累”——没有距离与体力数据，不能承诺。
2. “实时/最新/今天开放”——数据是历史公开资料，没有实时源。
3. “距离 X 公里/步行 Y 分钟/预计排队 Z 分钟”——图谱只有 NEXT 步骤顺序，没有道路网络与坐标。

### 1.3 非目标（Won't，与总规划 §2.4 一致）

- 不做全国景区、实时数据、票价、排队、天气、开放状态。
- 不做预订、支付、导航、叫车。
- 不做真实地图瓦片或坐标；只做**图谱示意图**（D3）。
- 不用 LLM 重写 P2–P6 的抽取结果；不让 LLM 生成开放时间/距离/票价/坐标。
- 不为 P4 增加算法或接进主链路（D4 冻结）。
- 不为好看删难样本、改评测数字。

## 2. 目标用户

### 2.1 P0 访客（默认服务对象）

| 画像 | 典型输入（原话） | 任务 | 成功标准（可观察） |
|---|---|---|---|
| 带娃家庭 | “带孩子去长隆玩一天，中午要吃饭” | 拿到一天能照着走的顺序，知道哪段没把握、孩子相关限制有没有数据 | 3 分钟内能说出“上午去哪、中午在哪吃、下午去哪、哪个点需要现场确认”；看到 1 条以上“未核验”提示 |
| 带老人家庭 | “带 70 岁老人去白云山，一天，少走路” | 不被安排过密行程；明确告知“少走路”无法用数据证明 | 页面出现人群提示与点数上限说明；不出现“已满足少走路”的断言 |
| 情侣 | “武功山两天，看日出，住山上” | 知道两天怎么分、日出/住宿有没有资料 | 分天卡片齐全；日出、住宿、夜间温度若资料没有，显示“资料未给出” |
| 朋友结伴 | “武功山两天，想走经典路线” | 拿到单一来源的完整路线骨架，能点开出处 | 每段连接可点到来源；partial 时能看到原因清单 |

P0 的统一成功定义：**用户能独立完成一次查询，并正确理解“哪部分有据、哪部分没据”**。不理解“没据”的部分，就算失败。

### 2.2 P1 评审（答辩/验收老师，以及组内 reviewer）

| 任务 | 成功标准 |
|---|---|
| 5 分钟内判断方法与证据链是否成立 | 能回答：这条路线来自哪几篇文档？状态为什么是 partial？哪些段没有来源？模型做了什么、没做什么？ |
| 判断限制是否诚实 | 页面与评审视图的限制说明与 [BASELINE.md](BASELINE.md)、P7 README 的已知限制一致，不夸大 |
| 判断可复现 | 能看到 intent、工具调用、逐段核验、图谱指标、请求耗时，且这些不含用户隐私原文 |

P1 的信息**默认不占 P0 首屏**（D2）。评审视图默认关闭。

## 3. 三条用户旅程

### 3.1 J1 访客首次查询（桌面与 375px 同流程）

| 步 | 系统行为（规格） | 页面要求 |
|---|---|---|
| 1 | GET 首屏，不触发模型 | 一屏内看到：主张、输入框、3 个示例、覆盖范围与限制入口。**不得**出现 JSON、trace、图谱指标 |
| 2 | 用户输入并提交 | 输入框保留原文；提交按钮变“处理中…”并可取消 |
| 3 | **≤3 秒**出现进度区（静态渲染，不等模型） | 四个阶段常显：`解析需求` → `查询图谱` → `规划路线` → `核验来源`；当前阶段高亮，已完成打勾，未开始置灰 |
| 4 | 返回结构化结果 | 顺序：状态徽标 → 免责句 → 人群/体力提示（有则）→ 行程卡 → 证据入口 → 地点列表 → 可修改操作 → 页脚限制 |
| 5 | 用户点任一停留点/任一段的“查看来源” | 证据卡展开，五个字段齐全（见 §6）；缺失字段显示“缺失”文案，不补造 |
| 6 | 用户改需求 | “去掉这个点 / 换一条备选 / 调整天数或人群”就地操作，不清空已输入 |

**成功标准**：3 分钟内能回答“先去哪、中午吃什么、下午去哪、哪一条没把握”；证据卡至少一条能打开原文域名。
**失败信号**：首屏出现 JSON/trace；30 秒无进度；状态徽标缺失；来源只有 `CL-T-02` 这类编号。

### 3.2 J2 追问补充（clarify 闭环）

| 步 | 系统行为（规格） | 页面要求 |
|---|---|---|
| 1 | 首轮信息不足，返回 `clarify` | 只问**缺的 1–2 项**，写在输入框上方；不重复问已答项（如已说“长隆”“一天”，就不再问景区/天数） |
| 2 | 用户补充（如“带上 3 岁小孩”） | 补充内容拼接到原需求，**保留首轮全部约束**（现状 `web_app.py:227–241` 已用 session `pending_query` 拼接，规格要求保留该行为） |
| 3 | 重新规划 | 人群提示置顶；若触发点数上限，按 §7.4 裁剪并说明“因带 3 岁小孩，已从 8 个点减到 6 个点” |
| 4 | 返回 `verified` 或 `partial` | 状态徽标 + 原因；不再追问同一字段 |

**成功标准**：一次补充内完成；已答信息不丢；追问总轮数 ≤2。
**失败信号**：重复问同一字段；把补充当新需求（丢掉原景区/天数）；追问 3 轮以上仍无结果（此时转 `clarify` 并给“换个问法/看示例”出口，不硬扛）。

### 3.3 J3 评审查看证据（auditor）

| 步 | 评审动作 | 页面要求 |
|---|---|---|
| 1 | 右上角切“评审视图” | 顶部显示：request-id、总耗时、状态、模型名与摘要（本机为 `qwen3:8b` / `local-qwen3-8b-q4_k_m`，见 BASELINE.md §5）、query 原文 |
| 2 | 看 intent 与约束检查 | intent JSON 默认展开（可复制）；约束检查给出 `ok/conflict/needs_clarification` 的判定与理由 |
| 3 | 看工具选择 | 每次工具选择的工具名、理由、调用耗时 |
| 4 | 看逐段核验表 | 表格：`from → to`、`source_doc_ids`、是否单一来源、是否通过；未通过段单独列表 |
| 5 | 看图谱指标 | `visits / steps / repeats / missing`，旁边固定注明“图谱 NEXT 步数，不是实际距离” |
| 6 | 看证据覆盖 | `N/M` 点/段有来源；缺失清单可直接跳到对应卡片 |
| 7 | 看 trace | 折叠，提供下载/复制；不显示本机绝对路径（见 §9 N8） |

**成功标准**：5 分钟内回答“依据哪几篇文档、哪些段没证据、为什么 partial、模型做了哪些决策”。
**失败信号**：指标要靠口头解释；trace 只有文件路径没有内容；无法区分“证据缺失”与“不适用”。

> 评审视图**不提供**“把 partial 改成 verified”的开关。状态只能由 CORE 的规则产生，不能人工改写（与 02_AGENT_PROTOCOL §6.1 一票否决项一致）。

**默认展开/折叠规则（一句话版）**：结果类（状态、免责句、人群提示、行程、证据摘要）展开；调试类（intent、工具、trace、图谱指标）不进入访客视图；长文本（摘句全文、地点全表、示意图）折叠并给计数。

### 4.2 移动端 375px 顺序（与桌面不同的只有 5 处）

1. 状态区上移到进度区正下方（先告诉用户“信不信”，再看内容）。
2. 行程卡先于任何指标/列表；每天默认只展开当天第一张，其余折叠。
3. 证据改为“停留点下方一行”：`来源 · doc_id · 发布日期 · 打开原文`，点开才是完整卡；日期缺失时写“发布日期未记录”。
4. 地点列表移到行程最后（避免首屏被长列表占满）。
5. 示意图默认折叠；视图切换收到页头图标，不占正文。

**硬要求**：375px 无横向滚动；表格类内容改为卡片；触控目标 ≥44×44px。

### 4.3 评审视图

- 入口：页头开关；地址可带 `?view=auditor` 直接进入；默认访客，刷新保持当前视图。
- 结构（自上而下）：页头（含 request-id/耗时/模型摘要）→ 状态与判定摘要 → intent JSON → 约束检查 → 工具选择与理由 → 路线候选与逐段核验表 → 图谱指标 → 证据覆盖统计 → trace（折叠/下载）→ 会话文件（相对路径）。
- 默认展开：状态、intent、逐段核验表、图谱指标。默认折叠：trace、原始候选路线全文。
- 评审视图只读；所有数字来自后端返回值，不在前端计算。

## 5. 状态语义

### 5.1 唯一的四个状态词

页面与接口只允许出现 `verified` / `partial` / `clarify` / `error` 四个值。**不新增同义词，不使用 `complete`、`working`、`reply`、`success`、`failed`。**

| 状态 | 定义（判定口径） | 徽标文案 | 一句话解释（副标） | 正文固定文案 | 示例 |
|---|---|---|---|---|---|
| `verified` | 路线中的**每一段** NEXT 连接都能在**同一篇**来源文档中找到依据（单一来源、逐段核验通过），且未触发截断/均分兜底 | `✅ 图谱连接核验通过` | 每一段“上一站 → 下一站”都能在同一篇来源里找到依据。 | 核验通过只证明连接有据，不证明一天走得完。开放时间、步行距离、排队、餐饮营业情况均未核验。 | “长隆亲子一日，N 个停留点，全部来自同一篇游记”（示例文案，非真实数据） |
| `partial` | 有可参考路线，但至少一项不成立：分天为均分兜底、路线被截断、存在无来源连接、子园区无园内 NEXT、多个来源拼接 | `⚠️ 部分可参考` | 有一条路线可看，但下面这些点没有完全通过核验。 | 下面列出原因（最多 3 条，其余折叠为“查看全部 N 条”）；不要把这条路线当成已证明可行的一天。 | “第 2 天按节点数均分，不是真实每日体力安排”；“第 3 段没有找到来源” |
| `clarify` | 输入不足以规划，或请求超出可处理范围（景区未覆盖、约束互相冲突且无法出方案） | `❓ 需要补充信息` | 还差 1–2 个信息才能给行程。 | 只问缺的项，逐条编号；不重复问已答项。 | “请告诉我：① 去哪个景区 ② 玩几天” |
| `error` | 系统侧失败：模型不可达/超时、返回无法解析、内部异常。**不产出任何可当作行程的内容** | `❌ 处理失败` | 这次没有生成行程，下面的内容都不是规划结果。 | 写明失败类型、已停止的动作、可重试或检查的具体对象；不贴原始异常堆栈给访客。 | “模型服务没有在 180 秒内返回，请求已停止” |

### 5.2 固定免责句（逐字，不得改写）

> 核验通过只证明连接有据，不证明一天走得完

- 位置：状态徽标正下方，字号 ≥14px，与正文同色，不用灰色小字。
- 出现条件：`verified` 与 `partial` 必显；`clarify`/`error` 不必显（因为没有行程）。
- 允许追加一句限定，但不得替换本句：“开放时间、步行距离、排队与餐饮营业情况未核验。”

### 5.3 颜色与图标（不以颜色为唯一信息）

| 状态 | 前景色 | 底色 | 图标 | 无障碍 |
|---|---|---|---|---|
| `verified` | `#1E6B34` | `#E8F5EC` | ✅ | 图标 + 文字双编码 |
| `partial` | `#8A5A00` | `#FFF4D6` | ⚠️ | 同上 |
| `clarify` | `#1F5FA8` | `#E7F0FB` | ❓ | 同上 |
| `error` | `#A12622` | `#FDECEA` | ❌ | 同上 |

对比度要求见 §9 N5；色值可由 T3.1 微调，但必须保持“深色字 + 浅色底 + ≥4.5:1”。

### 5.4 与旧状态值的迁移关系（D6）

| 旧值（当前代码/文档） | 新值 | 处理说明 |
|---|---|---|
| `complete`（`agent.py:207`、`220`；P7 README 第 121 行仍在用） | `verified` | 语义**收窄**：旧 `complete` 只表示逐段有 NEXT 证据，不表示可行；新 `verified` 沿用同一判定，但页面必须配免责句 |
| `partial`（`agent.py:199`） | `partial` | 语义不变；新增“原因清单”必填 |

| `error`（`agent.py:249`） | `error` | 不变；新增“不渲染半成品路线”约束 |
| `working`（`agent.py:98`） | **不作为状态** | 它是过程态，只出现在进度区阶段，不进入状态徽标；终态必须四选一 |

| 缺失 / `None` / 其他未定义值 | `error` | 前端不得默认成 `verified`；评审视图追加 `contract_violation=1` 标记，便于 T2.1 排查 |

### 5.5 判定禁止项

1. 不得因为“路线看起来顺”判 `verified`；只看逐段来源。
2. 不得因为“用户没抱怨”升级状态。
3. 不得把 `partial` 的均分天、截断段、无来源段藏在折叠区而不计数。
4. 不得由前端推断状态；状态由后端返回，前端只渲染。
5. 多来源拼接的整条路线最高只能到 `partial`（与 P7 现有“单一来源”规则一致）。

### 5.6 “连接核验”与“行程可行”分开（D6 落地方式）

页面**不新增第五个状态词**，用两个独立展示位表达：

| 展示位 | 内容 | 数据来源 | 位置 |
|---|---|---|---|
| 状态徽标 | 四值之一，回答“连接有没有据” | 后端 `status` | 结果区顶部 |
| 行程可行性说明 | **不是状态值**，一行固定文案 + 未核验项清单 | 固定文案 + `unknowns` 列表 | 状态徽标下方、行程卡上方 |

固定文案：

> 行程可行性：未核验。图谱只能证明“上一站到下一站有资料依据”，不能证明步行距离、开放时间、排队、餐饮营业与体力强度。

未核验项清单按实际缺项勾选显示：`步行距离` / `开放时间` / `排队时长` / `票价` / `餐饮营业` / `适龄与体力` / `住宿` / `日出日落`。有资料时该项不打勾，并链到对应证据卡。

## 6. 证据卡规格

### 6.1 每个停留点、每段连接显示什么

| 字段 | 内容 | 来源（只读） | 展示规则 |
|---|---|---|---|
| 标题 | 文档标题 | P1 元数据 `title` | 一行，超出省略，可点开 |
| `source_url` | 原文链接 | P1 元数据 `source_url` | 链接文字为 `打开原文 · {source_site 或域名}`；不显示裸长 URL；`rel="noopener noreferrer"`；新标签打开 |
| `publish_date` | 发布日期 | P1 元数据 `publish_date` | `YYYY-MM-DD`；不显示“刚刚/最近”等相对时间 |
| 原文摘句 | `clean_content` 的**连续子串** | P1 `clean_content` | 默认显示前 80 字，超出以“…”结尾；可展开全文；不改标点、不换行改写、不拼句 |
| `doc_id` | 来源编号 | P1 `doc_id` | 等宽小字，如 `CL-T-02`；多篇时全部列出 |
| 位置（评审视图） | 摘句在 `clean_content` 的起止字符位置 | 现有 span 口径（起点 0、结束不含） | 只读展示，**不新增或修改口径** |

**每段连接**额外显示：`from → to`、`source_doc_ids`、`是否单一来源`、`核验结果（通过/未通过）`。
**每段未通过**时，卡片头部为琥珀色条：`本段没有找到来源`，正文写“图谱里这条连接缺少可核对的来源，因此整条路线只到 partial”。

### 6.2 字段缺失时显示什么（不得编造）

| 缺失字段 | 显示文案 | 禁止动作 |
|---|---|---|
| 标题 | `来源标题缺失（doc_id: {doc_id}）` | 不得用正文首句冒充标题 |
| `source_url` | `原文链接缺失（数据缺口）` | 不得拼搜索链接、不得猜 URL、不得写“官网” |
| `publish_date` | `发布日期未记录` | 不得用今天/采集日期填充 |
| 摘句 | `无法定位原文摘句` | 不得用 LLM 生成“摘要”冒充原文 |
| `doc_id` | `来源编号缺失` | 不得编编号 |
| 整条来源 | 灰色「来源缺失」条 + `本条没有可核对来源，仅供参考` | 不得只隐藏卡片而不提示 |

统一规则：**缺失是合法结果**，显示“缺失”并计入评审视图 `evidence_missing` 统计；一篇文档都找不到时，该点/段最多只能支撑 `partial`，不能支撑 `verified`。

### 6.3 证据卡交互与计数

- 停留点内：摘要一行（标题 · 日期 · `doc_id` · 打开原文），点“查看原文摘句”就地展开，不跳页。
- 段内：默认显示“来源：`CL-O-01`（单一来源）”，点开显示完整卡。
- 每个证据区标题带计数：`本段 1 条来源` / `本点 2 条来源`；整份行程底部汇总 `证据覆盖 5/6 个停留点、4/5 段连接`。
- 同一 `doc_id` 重复出现时合并为一张卡，避免噪音。

### 6.4 禁止

1. 不改 `clean_content`、不重新断句、不改 `doc_id`（冻结项）。
2. 不显示无来源的“官方”“权威”“最新”字样。
3. 不把 P5 条件建议的营销话术当证据原文展示（T2.5 过滤后再展示）。
4. 不展示来源文档里的个人信息、联系方式、二维码。
5. 不在访客视图显示本机文件路径。

## 7. 行程卡规格

### 7.1 卡片结构（每天一张）

> 下面只是**排版示意**：地名为占位示例，时间与 `doc_id` 为占位符，不代表任何一次真实查询结果。

```
第 1 天 · 日期未指定 · 6 个停留点
─────────────────────────────
[人群提示条] 同行人：3 岁小孩、70 岁老人。图谱无适龄/体力标签，未做硬性过滤。
上午   09:30 到达 长隆野生动物世界南门       时长：资料未给出
       → 熊猫村（NEXT，资料步骤顺序）       证据：CL-T-02
中午   在 园区内餐厅 用餐、休息             时长：约 1–1.5 小时（模板估算）
下午   长隆欢乐世界 · 垂直过山车            时长：建议预留 2–3 小时（模板估算）
       本段没有找到来源 → partial
─────────────────────────────
本行程未核验：步行距离 / 开放时间 / 排队 / 票价 / 餐饮营业 / 适龄与体力
```

### 7.2 时间与时长（必须标依据）

| 情况 | 页面显示 | 依据标签 |
|---|---|---|
| P3 步骤 `time_source=explicit` | `09:30 到达 X` | `资料给出`（并给 `doc_id`） |
| 有模板区间（上午/下午 2–3 小时、中午 1–1.5 小时） | `时长：约 2–3 小时` | `模板估算`（**必须显示这四个字**） |
| 两者都没有 | `时长：资料未给出` | `未知` |

硬规则：
1. 有时间的显示时间；**没有时间就写“资料未给出”，绝不写推测钟点**。
2. `模板估算` 与 `资料给出` 必须视觉可区分（标签底色不同 + 文字），不能只给区间。
3. 时长区间只能来自：资料原文、`itinerary.py` 的固定模板、或明确的“未知”。不得按点数/距离换算。
4. 单日总时长不得给“合计 X 小时”，因为没有可靠叠加依据。

### 7.3 餐饮与休息

- 中午独立成块，标题固定 `中午 · 用餐与休息`。
- 图谱内有餐饮节点：显示名称 + `证据`；营业时间一律显示“营业时间未核验”。
- 图谱内无餐饮节点：显示 `图谱中未找到餐饮点；请在园区内选择营业餐厅。营业时间与排队未核验。`，**不得编造餐厅名**。
- 连续 3 个停留点无休息/餐饮块时，插入提示条：`已连续 3 个停留点没有休息安排，建议插入 15–20 分钟休息。`
- 下午返程/自由活动单独一行，只在资料或模板支持时出现，不写具体钟点。

### 7.4 体力/人群提示与点数上限（数值待签字，见 §11 Q4）

- 提示条位置：行程卡**最上方**，先于上午时段。
- 固定句：`图谱没有适龄、身高、体力标签，本行程未做硬性过滤，请按现场项目要求取舍。`
- 上限（提案，待签字）：默认 **≤8 个停留点/天**；同行人含 **<6 岁儿童或 ≥70 岁老人** 时 **≤6 个/天**；每 2 个停留点至少 1 个休息/餐饮块。
- 超限处理：自动裁剪到上限，并在状态区说明 `因带 3 岁小孩，已从 9 个点减到 6 个点`；被裁剪导致原需求未满足时，状态至少为 `partial`。
- 禁止：不得声称“已为老人/儿童优化路线”（没有标签，无法证明）。

### 7.5 每张行程卡必须显示的“未核验项”

固定一行，按实际缺项勾选（与 §5.6 同一清单）：`本行程未核验：步行距离 / 开放时间 / 排队 / 票价 / 餐饮营业 / 适龄与体力`。
有资料支持的项从该行移除，并在对应块旁边显示证据入口。

5. 不显示原始异常堆栈；技术细节只进评审视图与日志。
