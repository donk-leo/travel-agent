# 实验项目 7：程序性知识应用——旅游规划 Agent

## 一、目标与输入

使用项目 6 已构建的景区知识图谱，结合本地大语言模型和有限轮次工具调用，实现旅游需求解析、图谱查询、路线建议及来源追溯。主要输入为 `v0.6-p06` 的 `graph_nodes.csv` 与 `graph_edges.csv`。子园区标签另外参照 P1 已入库 CSV 的 `doc_id` / `subtype` 两列，整理成 `src/sub_area_scope.py` 中的 8 条常量并在测试中与 P1 对照；运行时不读取原文正文。本实验不读取原始游记。

## 二、方法与实现

- **交互及配置**：Flask 网页接收用户输入；Ollama 本地 `qwen3:8b` 通过 `/api/chat` 提供模型推理。模型和地址由 `P07_OLLAMA_MODEL`、`P07_OLLAMA_URL` 可选环境变量配置，默认使用本地服务。
- **需求解析与追问**：解析景区、天数、同行人群、偏好和限制。缺少规划所需信息时追问，网页通过会话暂存原需求。模型检查明显矛盾，出错或信息不足时提示，不把空结果伪装成路线。
- **工具调用与编排**：`agent.py` 根据需求让模型选择图谱工具，调用后将真实结果摘要反馈给模型，再决定结束或补查，最多 3 轮。工具由白名单限制；每次调用记录实际参数和返回值。`get_route_candidates` 以来源文档分组展示 `NEXT` 候选；`search_poi` 按景区列出或按关键词查找；`get_conditions` 读取条件建议；`neighbors` 提供节点出边查询。
- **路线生成与核验**：模型从候选连接提出节点序列；程序逐段检查有向 `NEXT`，缺少直接边时尝试通过图谱中的有向路径插入中间节点，再次逐段核验。补全路径时把已访问节点作为高代价节点，优先绕开它们。合理往返可保留；缺失实际距离、坡度、时长和适用性时应进一步确认。
- **单一来源与截断（2026-11-11）**：P6 的 `NEXT` 来自不同游记，跨文档拼接不能证明连续。`route_planner` 现在先按“用户点名地点数、连接完整度、官方优先”选一份来源文档，整条路线只使用该文档的边；若模型仍产生缺环，则截断到第一处缺环前的可核验前缀，并标记 `route_truncated=true`。跨文档或截断路线返回 `partial`，不再冒充完整路线。该版本同时把路线输出限制为最多 12 个节点，避免本地模型长输出超时。
- **路线整理（2026-11-09 优化）**：核验通过后，`tools.optimize_route` 保留模型起点；若终点是此前走过的地点（通常表示返程），也保留为终点；其余目标地点用 Held-Karp 动态规划（地点 ≤14）或贪心最近邻重排，使总 `NEXT` 步数最少。只有当结构成本（步数 + 2×重复次数）下降且重排后仍逐段核验通过时才采用新顺序，否则保留原路线。结果记录 `metrics`（访问数、步数、唯一地点、重复次数、缺失路段），并明确说明步数不是实际步行距离。
- **子园区范围（2026-11-09 优化）**：`scenic_aliases` 仍把“长隆欢乐世界”等写法归一为景区“长隆”；新增 `sub_area_scope` 记录子园区。文档级标签来自 P1 已入库 CSV 的 `doc_id`/`subtype`（8 条长隆文档），景点级归属由 P6 节点的 `source_doc_ids` 叠加该标签推导；出处跨园区或仅有综述文档时记为“未知”，不猜测。路线候选只保留该园区来源，景点列表按园区筛选；连接不足或图谱缺少节点（如飞鸟乐园）时回退整个景区并说明。多园区总览路线 `CL-O-01` 不纳入单园区规划。
- **约束传递与分时行程（2026-11-13）**：`plan_route` 显式接收 `profiles/preferences/constraints`，system prompt 要求逐条考虑，并在图谱无法证明适龄、步行距离、开放时间时写入 `uncertainties`，不得声称已满足。新增 `itinerary.py` 将已核验节点拆成上午/中午/下午，附时段时长提示；多日 `day_plan_fallback` 时每天标注“按节点数均分，不是真实体力安排”。行程说明明确图谱没有适龄/体力标签，未做硬性过滤。
- **结果及证据**：网页展示需求、决策摘要、查询范围、路线结构指标、路线、建议、分时行程和来源，可展开工具记录。新版 JSONL 保存输入、解析、决策摘要、工具调用与观察、子园区筛选、路线整理和最终结果。决策摘要不是模型内部思维链。历史记录可能为旧格式。

配置、依赖、运行和一条命令重跑案例见本项目 [README](../README.md)；接口定义见仓库 `standards/schema_tools.json` v1.2。v1.2 明确现有的按来源分组查询工具，并将返回字段写成结构化 Schema；P6 图谱未修改。上线或多人共享前需对接口变更进行组内复核。

## 四、失败现象、原因和后续方案

1. **理由串到其他建议**：早期模型返回某个编号，同时写了另一条建议的理由。现改为先按编号取回原建议，再针对单条建议生成理由；本次仍观察到“减少步行”等缺少实际距离证据的推测。后续可对理由的事实依据及条件进行标注和人工评测，不把模型推测当作图谱事实。
2. **模型编造直接连接**：白云山路线两处缺少 `NEXT` 边，重试仍未修复。现由程序查找图谱间接路径并逐段核验；2026-11-09 进一步给补全路径加“已访问节点”惩罚，并在核验通过后按 `NEXT` 连接整体重排（保留起点和返程终点）。重排能把亲子老人路线的重复次数从 6 降到 1，但图谱没有距离、坡度字段，仍不能从步数推导实际体力消耗。
3. **无匹配前误判**：曾对陌生景点名在查图谱前声称不存在。现将没有额外限制的普通信息查询交给图谱，未命中时说明“图谱中未找到”，不声称现实中不存在。模型对其他场景仍可能误判。
4. **范围和需求表达（已部分优化）**：图谱使用“广州白云山”，用户常说“白云山”；“长隆欢乐世界”等子园区名称此前只归一为“长隆”，查询范围仍会扩大到整个长隆。2026-11-09 新增 `sub_area_scope`：识别子园区，路线候选与景点列表优先限制在该园区，连接不足时回退并说明；归属由 P1 文档标签 + P6 `source_doc_ids` 推导，跨园区地点记为“未知”。仍存在的限制是：只覆盖长隆、飞鸟乐园缺少图谱节点、多园区总览路线不参与单园区规划；“朋友/同学/同事”等常见同行人已由关键词补全，但“两位 70 岁老人和一名 3 岁小孩”这类复杂表述仍可能漏。
5. **多日安排与实时信息**：早期版本的武功山两日请求没有逐日安排；当前已把 `duration_days` 传入路线规划并按 `day_plan` 分天展示，但模型分天不合法时仍按节点数均分，必须标 `day_plan_fallback=true` 并返回 `partial`，不能当作真实每日体力/住宿安排。票价、气候、日出时间、步行强度与开放状态仍不完整，信息缺失时继续说明。
6. **规划需求漏选路线工具**：网页体验中模型将白云山一日游识别为规划，却只选择建议和地点查询。现对规划请求补充路线查询，并将系统补充与模型选择分别记录；离线回归覆盖该分支，真实模型隔离网页测试也展示了经图谱核验的路线。
7. **距离、坡度数据缺口**：审核建议“补充距离、坡度数据后再比较实际体力消耗”。当前 P6 图谱没有这两类字段，P7 又只读图谱、不读原文，因此无法在不伪造数据的前提下换算体力消耗。本轮只增加 `NEXT` 步数与重复次数作为结构性代理指标，并在结果中明确标注。要真正比较体力消耗，需要 P2/P6 从原文抽取距离、坡度、台阶数等有来源的数据并重新打 tag。

## 五、可复现性及交付状态

运行 `python3 analysis/p07_agent/src/run_evaluation.py` 可重跑案例并生成新轨迹；运行 `python3 -m unittest discover -s analysis/p07_agent/tests -v` 可做离线回归；运行 `python3 analysis/p07_agent/src/analyze_route_optimization.py` 可对已有真实模型路线做确定性复算，输出整理前后对照。模型输出并非保证逐字一致。测试耗时及案例结果保存在原始结果文件，报告不将单次运行视为统计准确率。

用户于 2026-11-03 在对话中以审核人身份确认审核通过；2026-11-09 按审核意见完成子园区范围与重复路线两项优化，经确认直接合并，版本升为 `v0.7.1-p07`。2026-11-13 又在本地完成约束传递、分时行程、单来源/截断、会话保存权限和页面可用性修复；本段数字以当前工作区代码为准，提交后再按实际 commit 复核。交接卡的原 reviewer 字段按用户要求保留；该字段本身不表示其姓名对应人员已另行签署本次结论。
